What Should Embodied Agents Remember? Benchmarking and Evaluating Memory Modality for Embodied Agents

Junxiang Wang1,2† Yuchen Liu1,3† Yi Wu1 Guofei Chen1 Nir Pechuk2 Tao Chen1 Zackory Erickson2 Yuzhe Qin1 Tianyu Li1
1Dexmate 2Carnegie Mellon University 3Purdue University †Work done during an internship at Dexmate

Should a robot remember what it sees as text records, as generated descriptions of its camera frames, or as the frames themselves? MeMoREval measures how that choice affects task success and the inference cost of writing and reading memory. With our primary model, keeping the frames is both cheaper and more accurate than describing them.

Overview

What we contribute

1

A controlled protocol

Memory is written during a scripted experience; requests come later and are answered from memory alone, in a fresh context. Write-time and read-time inference costs are measured separately.

 2

A benchmark

53 tasks in four simulated indoor environments, covering seven kinds of information a robot must remember, with configurable memory modalities and backends.

 3

Reference evaluations

Six memory conditions on five backends with Gemini 3.7 Flash, checked on two more models, plus three deployment-oriented variants. For the primary model, frames give higher success than descriptions at lower write cost.

Protocol

Experience first, requests later

Every task has two phases. During the experience, the robot carries out a scripted sequence of actions while the memory module records what happens, without knowing which details later requests will need. During the request, the agent starts from a fresh context, receives no new observations, and has to answer or act from memory alone.

Backend

Organizes and retrieves memory: a transcript (a rolling log, no writer), a wiki (named pages the writer appends to and rewrites), or our adaptations of A-MEM, Mem0 and ObsMem. Every entry carries its step number, and the agent fetches archived artifacts by step.

2Request

Fresh context, no new observations

Information request

“Which cabinet contains the mug?” The answer is checked against a reference answer of a fixed type, such as a room or region, an object, a color, a count or a set.

Action request

“Fetch the mug.” The agent submits one complete plan of skill calls, executed open-loop and checked against the final simulator state.

Read-time cost per request: every model call while answering, also reported per successful request

Why open-loop plans

No observations come back while the plan runs, so the agent cannot make up for missing memory by searching the scene, for instance by opening cabinets until the mug appears. Success then measures what the memory retained.

Stacked histories

Because experience and requests are separate, tasks can be stacked: the experience phases of 10–11 tasks form one history of 37–100 steps, followed by their 21 requests. Each component task keeps its own grading.

Two costs, kept apart

Write-time cost grows with the actions a robot takes; read-time cost grows with the requests it receives. Their balance depends on the deployment, so we report both, in weighted tokens Tin·Pin/Pout + Tout, where T counts input and output tokens and P is the model’s price per token. Weighted tokens are proportional to dollar cost for a given model.

Benchmark

53 tasks in four environments

MeMoREval runs the protocol in the Genesis simulator, in four indoor environments adapted from SceneSmith scenes, each with seven to nine rooms and 200–300 objects. A simulated Dexmate Vega 1 bimanual mobile manipulator acts through skills for navigation, opening and closing furniture, and picking and placing objects. Every request is graded deterministically.

Seven kinds of information to remember

The categories describe the information a task depends on, not which memory modality is expected to do best.

Task gallery

One task per category, replayed from the robot’s head camera: what happens during the experience, the stored frames that hold the answer, and what is asked later. Every experience starts with the scene’s scripted tour, which the clips omit; the replays are sped up, with pauses cut.

Key frames in memory

Deployment-oriented variants

The controlled comparison uses short single tasks, a writer that receives only textual observations, and storage of every frame. Deployments can differ on each of these, and the benchmark evaluates such variants directly: backends respond differently to long histories and to the writer’s choices.

Release

Evaluate your own memory system

We plan to release the MeMoREval benchmark, the evaluation code and the reference memory implementations. Plug in a memory module and compare it with the reference configurations under the same protocol.

  1. 1

    Implement the memory interface

    Your module receives each experience step’s observations, decides what to retain and in which form, and serves the agent at request time through the memory text placed in its prompt and the retrieval tools it can call.

  2. 2

    Run the protocol

    Once released: 53 single tasks and four stacked histories in four simulated environments, with the same model as writer, describer and agent for every condition you compare. The experience is fixed per task, so differences reflect your memory design.

  3. 3

    Compare

    Success by category and request type, with write-time and read-time costs, side by side with the six reference conditions and five backends run with the same model (costs are comparable only within a model).
